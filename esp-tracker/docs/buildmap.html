There are two working backends. They share the schema and the contracts and nothing else, so the first question before any change is which one am I editing.

Why the ladder had to change. A Vercel function is killed the moment it returns its response, so a coroutine that sleeps for 300 s cannot exist. Pending rungs became rows with a due_at. That fixed a real latent weakness at the same time: the asyncio version lost every pending escalation on restart, and rows survive.

Rung 1 is deliberately not queued. pg_cron granularity is 60 s, so a queued rung due at t+60 fires somewhere in t+60..t+120. Acceptable for the secondary SMS and the voice calls — but the first alert must never wait for a scheduler, so it is sent synchronously inside the ingest request.

Path A — before any real data

RLS is the entire security model. Supabase exposes every table over PostgREST using the anon key, which ships in your frontend bundle. A table without RLS enabled is readable by anyone who opens devtools. For a live database of a child's location that is not a misconfiguration — it is the worst outcome this project has.

0002_rls.sql enables RLS on all fourteen tables, with policies routed through device_access. Three tables — alert_queue, access_log, integration_health — get no policies at all: RLS on with nothing matching means they are invisible to everyone but the service role. Verify in the Table Editor before real data goes in.

The service role key bypasses RLS entirely. It lives in supabase secrets and Vercel environment variables. Never in web/, never in git, never in a client.

02

Contracts — change anything but these

Everything else in this system is a preference. These five are load-bearing: each one exists because breaking it produces a failure that looks like something else, which is the expensive kind.

1
Transmit the SOS at t+5 s with whatever fix exists
Indoors the GNSS branch never returns. Waiting for fix quality is a design that never fires inside a school. SOS_TX_DEADLINE_MS
2
HTTP 200 is the only ack
An event leaves the device's flash queue on 200 and on nothing else. "The request was sent" is not delivery, and a dropped SOS is unrecoverable.
3
Every event carries an id; ingest is idempotent
2G retries constantly. A redelivery must never become a second position on the map or a second attendance record. Enforced by UNIQUE(event_id).
4
A position is never rendered without source, accuracy and age
A 12 m GNSS fix and a 2 km cell estimate are both "a pin" if you let them be. This is the most dangerous bug available in this system.
5
One press is one alert
The device texts the parent directly. When it reports device_sms_sent, the server skips its own t+0 SMS. Two texts for one press teaches parents to distrust the alert.

07

What is provisional

Four parts are stand-ins for something else. Each is a deliberate trade, and each is worth revisiting when stock allows.

WantedFittedWhat it cost
SIM7080G (LTE-M)SIM800L (2G)No modem TLS, battery 5 days → 2–3. Bought SMS as an unkillable channel. Correct part for PH regardless
LIS3DH accelerometerWi-Fi + cell motion gate~0.5% battery and no interrupt wake. Arguably a better signal — jostling isn't movement
Vibration motorLED + piezoThe one substitution that is purely worse. Haptics are the only channel both silent and felt
Google FMDN fallbacknothingA tracker that is off or out of coverage is simply gone. Deliberate — see the companion page
Before touching the feedback code

SOS cues are silent on purpose. A piezo is a better stand-in than an LED for most things, because sound reaches a child who is not looking. But an SOS is the one case where being heard can be the danger: a child presses the button precisely when someone is frightening them, and a device that then beeps announces both the child and the fact that they called for help.

So the piezo carries boot, low battery, drill mode and "locate now"; the SOS cues stay visual. If you set FEEDBACK_SILENT_SOS = false, understand that is the trade you are making.
