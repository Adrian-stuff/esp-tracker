Setup Guide

How the child tracker system works, from unboxing to a parent seeing their child on the map.

1. Architecture

The system has four components that talk to each other over SMS and WiFi:

Parent → Dashboard → Supabase → SMS → Tracker
Tracker → SMS → Scanner → Supabase → Dashboard

Tracker

ESP32 + SIM800L (2G) + GPS module. Worn by the child. Sends location via SMS. Has an SOS button.

Scanner

ESP32 + RC522 RFID + SIM900. Mounted at the school gate. Reads student cards, relays tracker SMS to the cloud.

Supabase

Cloud backend. Stores locations, attendance, SOS events. Runs Edge Functions for data processing.

Dashboard

Web app for parents. Shows live map, attendance, SOS alerts. Pairs to a tracker via claim code.

2. Data flows

Card tap → Attendance

Card taps reader → Scanner queues tap → ingest function → Dashboard shows it

Direction (in/out) is computed server-side by ordering the day's taps: odd = in, even = out. This self-corrects for late arrivals.

Tracker position → Map

GPS / WiFi scan → LOC SMS → Scanner relays → locations table

Two SMS messages go out: LOC (GPS coordinates) and WIFISCAN (nearby WiFi networks). The WiFi scan is what enables indoor positioning — the server matches BSSIDs against named places.

SOS button

Parent holds 2s → SMS to parent + SMS to scanner → Dashboard SOS banner

The SOS goes to both the parent (direct) and the scanner (relayed to Supabase). The dashboard shows a pulsing red banner. The parent acknowledges to stop the escalation ladder (secondary SMS, then voice calls).

Locate now

Dashboard button → locate function → LOCATE SMS → Tracker wakes, gets fix, replies

3. Three connections

For the system to work, three things must be linked:

ConnectionHowWhere stored
Card → Child Card writer tool or SQL cards table
Child → Parent Claim code on dashboard device_access table

4. Step-by-step setup

Step 1: Supabase

  1. Verify migrations are applied: supabase migration list --linked
  2. Set secrets: supabase secrets set ROSTER_SALT=... SMS_CMD_SECRET=...
  3. Deploy functions: supabase functions deploy relay-sms --no-verify-jwt (and all others)
  4. Insert demo devices and cards via SQL Editor (see below)

Step 2: Flash firmware

python3 -m platformio run -t upload -e tracker   # tracker
python3 -m platformio run -t upload -e scanner   # scanner

Step 3: Connect scanner to WiFi

  1. Power on scanner
  2. Connect phone to "Tracker-Scanner" WiFi (open)
  3. Captive portal opens at 192.168.4.1
  4. Select school WiFi, enter password

Step 4: Configure tracker & pair to dashboard

Option A — WiFi captive portal (recommended):

  1. Power on the tracker while holding the SOS button (hold for 2+ seconds until the LED blinks blue)
  2. Connect your phone to WiFi network "Tracker-Setup" (open, no password)
  3. Browser opens automatically to the config page (captive portal)
  4. Enter SOS number, scanner number, and child's name
  5. Tap "Save & reboot" — tracker saves and restarts
Tip: If the captive portal doesn't open automatically, go to 192.168.4.1 in your browser. The config portal times out after 5 minutes and reboots.

The portal also shows a "Connect to dashboard" panel with the device ID, claim code, and a link to the dashboard. The parent can immediately sign up and enter the claim code to pair.

Option B — BLE: Connect with nRF Connect, send to FFF2:

SCANNER +639325762230
SOS +639109943152
WIFI   (enters config mode remotely)

Option C — SMS: Text the tracker's SIM:

5Mz4hXMEQVVGt77MOGjJVMHglz8RaQ4h SCANNER +639325762230
5Mz4hXMEQVVGt77MOGjJVMHglz8RaQ4h SOS +639109943152

Step 5: Register cards

Use the card writer tool (scanner-uno/card_writer/card_writer_gui.py). It writes the physical card AND registers it in Supabase automatically.

Step 6: Parent pairs their account

The claim code is shown in the WiFi config portal's "Connect to dashboard" panel. For reference:

  1. Open the dashboard
  2. Sign up with email + password
  3. Enter claim code: TRACK-DEMO-2026
  4. Tracker appears on the map

9. Security

  • SMS_CMD_SECRET prevents unauthorized reconfiguration of the tracker
  • ROSTER_SALT hashes card UIDs so the roster can't be enumerated
  • Per-device tokens (SHA-256) — one compromised device can't affect others
  • RLS on all tables — dashboard shows only paired devices
  • MIFARE Classic UIDs are cloneable — card security is a deterrent, not encryption
  • WiFi config portal is open (no password) but only active for 5 minutes per boot, and only when SOS button is held at power-on
